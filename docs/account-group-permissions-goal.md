# Account, group, and permission lifecycle

## Coverage verdict

**Implemented for applications using `SqliteIdentity.layer` and `IdentityBundle`.** The contracts are native RPC operations, backed by a separate application-private SQLite identity database. The demonstration apps supply seeded accounts; users can also register. These operations are an explicit, bounded identity and access implementation, not a production IdP, email recovery service, or automatic grant for every Resource.

| Requested use case | Published operation and behavior |
| --- | --- |
| Sign in | `identity.login` verifies an Argon2id password and issues an expiring opaque session. Every protected call checks current account state. |
| Sign out | `identity.logout` revokes the presented session; it does not sign out every device. |
| Sign up | `identity.signup` creates an isolated tenant with its first admin, or consumes a single-use tenant invitation issued by an existing admin with `identity.issueInvite`. An invited registrant joins as a reader. The signup result contains a new session. Existing and closed usernames cannot be reclaimed. |
| Close account | `identity.close` disables the authenticated account and revokes all its sessions in one transaction. It preserves the username tombstone and does not delete application-owned records. |
| Reset password | A current tenant admin obtains a 15-minute one-use credential via `identity.issuePasswordReset`; the recipient redeems it with public `identity.resetPassword`. Replacement and revocation of all existing sessions are atomic. The credential is returned to the admin for out-of-band delivery, not emailed or issued anonymously. |
| Create, update, delete group | `identity.group.create`, `.update`, `.delete` manage tenant-scoped named groups. Mutations require a current tenant administrator; delete also removes memberships and group grants. |
| List members, is member?, add member, remove member | `identity.group.listMembers`, `.isMember`, `.addMember`, `.removeMember` operate on persisted same-tenant active accounts. Administrators mutate membership; self/member reads are restricted. |
| Account-based permissions | `identity.permission.grantAccount`, `.revokeAccount`, `.listAccount` manage direct, tenant-scoped permission names. Administrators mutate grants; users can list their own direct grants. |
| Group-based permissions | `identity.permission.grantGroup`, `.revokeGroup`, `.listGroup` manage group grants. `identity.permission.check` resolves direct **or** current group grants for the authenticated account, denying absent grants. Membership removal, grant revocation, group deletion, account closure, and token revocation take effect on the next request. |

The [portable identity contract](../packages/effect-domains/src/identity/index.ts), [native identity and group RPCs](../packages/effect-domains/src/identity/rpc.ts), [group policy service](../packages/effect-domains/src/identity/groups/index.ts), and [SQLite identity storage](../packages/effect-domains/src/identity/sqlite/index.ts) keep these management semantics out of canonical application Resource schemas. The [Team Tasks review command](../examples/team-tasks/review.ts) uses the narrow `GroupRuntime` to require `todos.review` before reading the tenant-wide aggregate; ordinary task owner/tenant policies remain unchanged. Roles on demonstration accounts are **not** persisted groups. Other application operations must opt into permission checks explicitly.

The identity store retains its `001_initial` history and explicitly migrates existing accounts and sessions to the `002_account_groups_permissions` tables; its migrations remain separate from application database migrations. [Migration regression](../test/IdentityMigration.test.ts), [identity lifecycle regression](../test/IdentityLifecycle.test.ts), and [group/command regression](../test/TeamTaskGroups.test.ts) cover upgrade/restart, invitation and reset expiry/replay, tenant boundaries, group mutations, effective access, and revocation.

**Verification (2026-09-25):** `bun run --filter effect-domains check`, `bun run --filter effect-domains lint` (83 source files under the 500-line limit), and `bun run test` (159 tests in 35 files) passed. A VitePress build passed after the identity documentation changes. A live Team Tasks CLI run with isolated task/identity SQLite files checked an existing group grant, restored Bob's membership, received `{ "total": 1, "completed": 0 }` from `todos.review`, restarted the server, confirmed persisted membership/access, revoked the group grant, and observed effective permission `false`. The same CLI issued an invitation, joined Acme as a reader, issued/redeemed a password reset, and confirmed old-session revocation and account closure. The generated browser displayed the new operations; signup populated the memory-only bearer, `identity.current` resolved the new account, and close cleared it.

These observations establish local SQLite/CLI/browser behavior, not production credential delivery, multi-node identity operation, or inferred authorization for every Resource.
