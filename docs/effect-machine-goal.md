# Effect Machine: what is worth taking

**Recommendation: borrow its approach to *transient interaction state*, not its actor runtime as a new Effect Domains foundation.** Effect Machine solves a different problem: one actor owns a tagged state, processes events serially, and owns work whose lifetime depends on that state. Effect Domains derives persistent resources and operation contracts, while leaving business transitions and durable execution explicit. Those models can complement each other; replacing `Resource.transitions` or native Effect Cluster with machines would lose important existing guarantees.

This analysis uses Effect Machine **v0.27.0**, pinned to [commit `0a533e8`](https://github.com/cevr/effect-machine/commit/0a533e82356b6f3d3246eef34a53d2996b701a73). Both projects currently pin Effect `4.0.0-rc.112` ([upstream package](https://github.com/cevr/effect-machine/blob/0a533e82356b6f3d3246eef34a53d2996b701a73/package.json); [local package](../package.json)). Compatibility of the Effect version is encouraging, but it is not evidence that the two application models should be merged.

## Feature inventory and fit

| Effect Machine feature | What we could gain | Fit for Effect Domains |
|---|---|---|
| **Schema-defined, variant-specific state and events.** `State` and `Event` produce tagged unions; each phase can have different valid fields. `State.with` carries shared fields into a new variant. Initial input and final output are distinct from actor state. [Source](https://github.com/cevr/effect-machine/blob/0a533e82356b6f3d3246eef34a53d2996b701a73/src/schema.ts); [Effect model](https://github.com/cevr/effect-machine/blob/0a533e82356b6f3d3246eef34a53d2996b701a73/docs/effect-model.md). | Strong fit for a **bespoke, multi-phase browser interaction**: for example, an intake flow in which customer lookup, editing, submission, and completion have different data and permitted inputs. Poor fit for a canonical SQLite row merely because it has a `status` field. |
| **Guarded transitions and stabilization.** `.on`/`.when` select ordered candidates; guards can be Boolean or Effects with service requirements. `.immediate` settles eventless transitions before publishing a stable state; `.reenter` restarts state-owned work. Unhandled events leave the state unchanged, and an accidental immediate loop defects after 100 edges. [Builder](https://github.com/cevr/effect-machine/blob/0a533e82356b6f3d3246eef34a53d2996b701a73/src/machine.ts); [selection](https://github.com/cevr/effect-machine/blob/0a533e82356b6f3d3246eef34a53d2996b701a73/src/internal/transition.ts). | Useful for interaction protocols. **Not equivalent** to our named invalid-transition error: [`Transitions.make`](../packages/effect-domains/src/transitions.ts#L117-L216) describes allowed changes to one persisted literal field, and repository mutation applies authorization and a conditional status/version write ([contract](wiki/tables-and-queries.md#generated-resource-capabilities)). |
| **State-owned asynchronous work.** An Effectful transition blocks one mailbox step; `.task` converts a typed success/failure into an event; `.spawn` owns a listener, stream, or child until state exit; `.timeout` cancels on exit; `.background` lasts for the actor; `.postpone` defers an event until state changes. [Async-work guide](https://github.com/cevr/effect-machine/blob/0a533e82356b6f3d3246eef34a53d2996b701a73/docs/async-work.md). | **Most valuable transferable idea:** make the lifetime of an interactive lookup, timer, or subscription follow the phase that needs it. This does not make a database transaction, external effect, or scheduled reminder durable. |
| **Serialized actor protocol.** `send` queues and returns; `call` awaits processing information; schema-replied `ask` supports immediate or deferred answers. Actors expose snapshots, waits, final output, exit state, and a host callback client. The process-local mailbox is **unbounded**. [Actor API](https://github.com/cevr/effect-machine/blob/0a533e82356b6f3d3246eef34a53d2996b701a73/src/actor.ts); [queue](https://github.com/cevr/effect-machine/blob/0a533e82356b6f3d3246eef34a53d2996b701a73/src/internal/runtime.ts). | Can simplify races among events **within one local session**. Our published operations already have typed RPC contracts; an actor mailbox is not a substitute for database conflict detection, authentication, or distributed routing. |
| **Actor topology.** Named actor systems support lookup/watch; child actors can be owned by a parent state. `ActorHost` lazily starts a child requested by consumers while its parent state owns shutdown. [Actors guide](https://github.com/cevr/effect-machine/blob/0a533e82356b6f3d3246eef34a53d2996b701a73/docs/actors.md); [host source](https://github.com/cevr/effect-machine/blob/0a533e82356b6f3d3246eef34a53d2996b701a73/src/actor-host.ts). | Situational for an authored screen with genuinely independent, short-lived child sessions. `ActorHost` is **not an HTTP host** and supplies no session authorization. Do not turn every `Resource` into an actor. |
| **Recovery and supervision.** A local actor can resolve its starting state, save transitions through application-supplied hooks, and restart defects within an Effect `Schedule` budget. Restart uses initial state or recovery—not the last in-memory state—and pending requests fail. [Guide](https://github.com/cevr/effect-machine/blob/0a533e82356b6f3d3246eef34a53d2996b701a73/docs/persistence-and-supervision.md); [supervision](https://github.com/cevr/effect-machine/blob/0a533e82356b6f3d3246eef34a53d2996b701a73/src/supervision.ts). | Good vocabulary for an application-owned actor’s failure contract. Not a reason to replace our native durable workflow, outbox, or SQLite transaction boundaries. |
| **Cluster entity adapter.** `toEntity` derives send/ask/state/watch operations; an entity can map its ID to machine input and use snapshot or journal persistence through an adapter. [Cluster guide](https://github.com/cevr/effect-machine/blob/0a533e82356b6f3d3246eef34a53d2996b701a73/docs/cluster.md); [protocol](https://github.com/cevr/effect-machine/blob/0a533e82356b6f3d3246eef34a53d2996b701a73/src/cluster/to-entity.ts). | Low framework value. Effect Domains already composes native Entity, Workflow, scheduling, and EventLog where their semantics are needed ([current direction](wiki/research-agenda.md#adjacent-native-api-decisions)). This adapter helps only if an application **already has** a machine-shaped, identity-local entity. |
| **Atom integration.** Writable actor Atoms and equality-based selectors give React/Solid components precise subscriptions; `can(event)` can drive a reactive *preview* of a guard. Terminal state can retain values needed during exit animation. [Atom/UI guide](https://github.com/cevr/effect-machine/blob/0a533e82356b6f3d3246eef34a53d2996b701a73/docs/atom-and-ui.md); [implementation](https://github.com/cevr/effect-machine/blob/0a533e82356b6f3d3246eef34a53d2996b701a73/src/atom.ts). | Attractive for **authored actor-backed UI**, not a default dependency for our framework-neutral generated UI. The latter currently renders inspected forms/lists and makes explicit requests ([UI contract](wiki/tables-and-queries.md#commands-applications-and-application-ui); [browser dependencies](../apps/application-ui/package.json)). `can` must never be treated as server permission: the actor checks again, and our server must still authenticate, authorize, and guard the write. |
| **Live inspection.** Typed events cover received events, guard results, accepted operations/transitions, task outcomes, defects, stops, and actor generations. An inspector can attach to one actor or observe future events system-wide; console, tracing, and collection implementations exist. [Inspection guide](https://github.com/cevr/effect-machine/blob/0a533e82356b6f3d3246eef34a53d2996b701a73/docs/inspection.md); [source](https://github.com/cevr/effect-machine/blob/0a533e82356b6f3d3246eef34a53d2996b701a73/src/inspection.ts). | A useful **opt-in runtime diagnostic pattern** for authored interactions. It is different from our existing, static [`ApplicationIR` inspection](../packages/effect-domains/src/application-inspect.ts), which describes schemas, policies, transitions, and tables to adapters. Feed bounded, redacted outcomes into existing OTLP instrumentation; raw actor states or events could contain secrets. |
| **Transition-path testing.** `simulate`, a stepwise harness, and path assertions exercise supplied event sequences. Their simulator does **not** run tasks, timers, backgrounds, or live resource cleanup; its Effectful transition handlers *do* run. [Testing guide](https://github.com/cevr/effect-machine/blob/0a533e82356b6f3d3246eef34a53d2996b701a73/docs/testing.md); [source](https://github.com/cevr/effect-machine/blob/0a533e82356b6f3d3246eef34a53d2996b701a73/src/testing.ts). | Borrow the **test distinction**, not necessarily the harness: fast path checks for a transient protocol; real actor tests for cancellation; authenticated RPC/SQLite tests for persisted domain transitions and conflicts. |

## The boundary that matters

Effect Domains already has the *persistent* part that the appealing machine diagrams might suggest is missing. `Resource.transitions` supplies a declared status graph and derived guarded writes. `Command.implement` owns semantic, cross-record work. Support Cases puts its lifecycle and event/audit writes into authored transactional commands, rather than assuming a status change implies those side effects ([framework contract](wiki/research-agenda.md#implemented-contract); [Support Cases description](wiki/research-agenda.md#application-evidence)). I ran `bun run examples/support-cases/main.ts inspect support.advanceCase`: the output includes its action input, version requirement, typed conflict/invalid-transition errors, and the resource’s separate inspected transition graph. That is substantial existing coverage, not a blank state-machine slot.

Conversely, our generated Application UI does **not** model a multi-phase, state-owned interactive session, maintain fine-grained selected actor subscriptions, or stream live entity state ([UI implementation](../apps/application-ui/src/client.ts#L1014-L1030); [documented boundary](wiki/research-agenda.md#adjacent-native-api-decisions)). A separate application-owned intake now probes the first gap, without turning it into a generated contract. Effect Machine's function-valued guards and effects cannot be losslessly compiled from a canonical domain schema into SQL policy, durable business transitions, or inspectable `ApplicationIR` merely by adopting the library.

## Important limits before copying persistence code

This is where source inspection changes the recommendation:

1. **A local durability hook is not an atomic commit.** The runtime publishes the next state and notifies subscribers before its state-change/durability hook completes ([processing order](https://github.com/cevr/effect-machine/blob/0a533e82356b6f3d3246eef34a53d2996b701a73/src/internal/runtime.ts#L916-L970)). `call` can wait for that hook; `send` does not supply commit acknowledgement. An observer can therefore see state that has not been saved. Keep SQLite as the authority for business records.
2. **The supplied Cluster persistence backend is in-memory, not a production SQL store** ([export](https://github.com/cevr/effect-machine/blob/0a533e82356b6f3d3246eef34a53d2996b701a73/src/cluster/index.ts); [adapter](https://github.com/cevr/effect-machine/blob/0a533e82356b6f3d3246eef34a53d2996b701a73/src/cluster/adapters/in-memory.ts)). Snapshot-mode saves run asynchronously and ignore save failures; journal mode does not apply the configurable periodic snapshot schedule, taking a snapshot on deactivation instead ([implementation](https://github.com/cevr/effect-machine/blob/0a533e82356b6f3d3246eef34a53d2996b701a73/src/cluster/entity-machine.ts#L210-L253); [configuration](https://github.com/cevr/effect-machine/blob/0a533e82356b6f3d3246eef34a53d2996b701a73/src/cluster/persistence.ts#L40-L58)).
3. **Do not interpret its journal as an exact business event log.** The RPC path processes a `Send`/`Ask` before appending its journal entry; the append is before the successful RPC reply, but state has already advanced. Its regression accepts recovery of **at least three** increments after the fourth append fails, explicitly allowing the advanced state to appear in a deactivation snapshot ([RPC ordering](https://github.com/cevr/effect-machine/blob/0a533e82356b6f3d3246eef34a53d2996b701a73/src/cluster/entity-machine.ts#L257-L314); [regression](https://github.com/cevr/effect-machine/blob/0a533e82356b6f3d3246eef34a53d2996b701a73/test/integration/cluster-persistence.test.ts#L423-L487)). Internal task/timeout-generated events also do not travel through that inbound RPC journaling branch. Our authored outbox and native EventLog slices address different, explicitly bounded guarantees ([native execution contract](wiki/tables-and-queries.md#native-durable-execution)).
4. **Replay needs effect discipline.** Simulation and replay can execute Effectful transition handlers while omitting actor-owned tasks and resources. An external side effect inside a replayed transition is therefore not automatically safe ([replay](https://github.com/cevr/effect-machine/blob/0a533e82356b6f3d3246eef34a53d2996b701a73/src/machine.ts#L1489-L1549)). Also, schema variant constructors do not decode untrusted input; decode at transport/storage boundaries ([schema implementation](https://github.com/cevr/effect-machine/blob/0a533e82356b6f3d3246eef34a53d2996b701a73/src/schema.ts#L262-L371)).

## Recommended order

1. **Keep the published package in one *application-owned, transient* interaction only where it earns its cost.** The [Support Cases intake](../examples/support-cases/README.md#use-the-application-ui-guided-intake-or-mcp) now probes phase-specific input, cancellable customer lookup on back-navigation, and one final existing command that performs the authoritative write. Keep its actor out of canonical resource schemas and the database authority. The [actor tests](../test/SupportCaseIntake.test.ts) exercise cancellation, invalid-phase events, and concurrent submissions; authentication and writes stay at the server operation boundary. Browser reload discards the draft but cannot roll back a committed request. If a plain scoped Effect and local state prove simpler for a subsequent interaction, do not retain a machine there.
2. **Borrow the lifetime and diagnostic rules without importing the DSL into the framework.** State-scoped tasks versus application-lifetime work, explicit typed failure-to-event conversion, and redacted transition/task outcomes are useful design checks for a complex authored interface. Existing Effect scopes and OTLP already provide the implementation substrate.
3. **Use selector Atoms or Cluster `watch` only for a demonstrated live-interaction requirement.** The React/Solid examples test that unrelated selections do not rerender; they do **not** establish a latency or throughput improvement for our generated UI ([React test](https://github.com/cevr/effect-machine/blob/0a533e82356b6f3d3246eef34a53d2996b701a73/examples/react/src/selector-performance.perf.tsx); [Solid test](https://github.com/cevr/effect-machine/blob/0a533e82356b6f3d3246eef34a53d2996b701a73/examples/solid/src/selector-performance.perf.tsx)). Live server state would additionally need an explicit authenticated subscription and invalidation contract.
4. **Do not port its generic actor system, Cluster persistence, or event journal into Effect Domains.** They would duplicate native execution machinery while weakening or obscuring our existing SQL authorization, version checks, migration ownership, and application-specific reconciliation policy.

If “copying” means literal source reuse, the upstream project is [MIT licensed](https://github.com/cevr/effect-machine/blob/0a533e82356b6f3d3246eef34a53d2996b701a73/LICENSE), with its copyright and permission notice required in copies or substantial portions. **Using the optional dependency for a bounded application probe is preferable to vendoring its actor runtime.**

## Implemented probe and its limit

The [example route](../examples/support-cases/intake-route.ts) mounts `/intake` alongside the generated `/` UI; [the protocol](../examples/support-cases/intake-machine.ts) owns only one page's interaction, with `LookingUp` and `Submitting` tasks scoped to their phases. [The client](../examples/support-cases/intake-client.ts) sends same-origin operation calls and decodes returned customer/case data at the browser boundary. It does not import a machine into `effect-domains`, persist actor state, use Cluster, or infer business transitions from the actor. The server's `support.openCase` remains public in this demonstration; protected `support.auditTrail` still denies anonymous requests. An interrupted or failed submission is **ambiguous** until the authoritative case list is checked, so the UI does not automatically retry. [Dated verification](wiki/validation-strategy.md#2026-09-25-transient-case-intake) records the exercised scope.

## How to offer interactions in Effect Domains (proposal, not implemented)

The current probe exposes a gap in the **browser adapter**, not in the canonical Resource model. `ApplicationIR` contains published RPC contracts and resource transition inspection, but no browser-phase protocol ([compiler product](../packages/effect-domains/src/application.ts); [inspection](../packages/effect-domains/src/application-inspect.ts)). The generated UI's presentation accepts labels, descriptions, and columns—not executable interaction modules ([presentation contract](../apps/application-ui/src/contract.ts)); its operation form invokes one RPC at a time ([client](../apps/application-ui/src/client.ts)). Support Cases therefore owns its own route, bundling, request adapter, token-independent public flow, actor startup/cleanup, and rendering. Those seams—not `Machine.make`'s transition DSL—are where a reusable offering could earn its place.

Today `ApplicationUiAssets` accepts one prebuilt JavaScript string and one stylesheet, and `ApplicationUi.register` serves only those, the metadata endpoint, and `/api/call` ([adapter](../packages/effect-domains/src/application-ui.ts)). Loading separately built interaction modules therefore needs a deliberate asset manifest and noncolliding route registration; a server-side `import()` of an authored view is not an acceptable browser bundle strategy.

| Candidate | Benefit | Cost / misuse risk |
| --- | --- | --- |
| Add an `Interaction` part and compile Effect Machine handlers into `ApplicationIR` | One discoverable framework-wide catalog; a fully declarative subset might admit generic forms and inspection. | Effectful guards, tasks, presentation, and failure recovery are not lossless schema transformations. It would either duplicate Effect Machine as a thin wrapper or claim static semantics it cannot inspect. Browser lifetime and server persistence would be conflated. **Do not implement from one slice.** |
| Add an **opt-in generated-UI interaction host**, leaving machines authored by applications | Share in-memory credentials, existing RPC dispatch, accessible navigation, bundle delivery, Effect scope/actor cleanup, and error handling without moving business policy. Generated forms remain the default. | Needs a real second consumer, a typed browser RPC boundary, asset/route validation, and a safe way to close a panel during logout. A module callback is an explicit UI escape hatch, not a declarative domain model. **Preferred experiment.** |
| Derive action affordances directly from `Resource.transitions` | Already-inspected graph could preview permitted edges for a row with a **published** transition operation. | Not a multi-phase interaction. Support Cases deliberately does not publish a generic `support_cases.transition`: `support.advanceCase` owns assignment checks and transactional history. Status and local `can` never replace server authorization or version checks ([transition source](../examples/support-cases/resources.ts); [command](../examples/support-cases/sqlite.ts)). Keep this separate from the interaction host. |

**Proposed UI-only contract:** `ui.interactions` registers a stable ID, label, and prebuilt same-origin browser module. That module runs in an Effect scope tied to the selected generated-UI panel and may author a machine with the optional `effect-machine` dependency. The host supplies a narrow operation caller backed by the existing `/api/call` boundary and the generated UI's **in-memory**, request-local bearer; its API does not hand the module a bearer string. Same-origin application-authored browser code is trusted code, **not** a token isolation boundary. A static UI manifest can expose IDs, labels, and declared operation names, validated against `ApplicationIR.group` at startup. It must not claim to inspect function-valued transition behavior or add phases to canonical schemas. The actual module API, particularly a typed return/error codec without importing server handlers into a browser bundle, remains to be proven by the second slice.

The lifecycle contract should be explicit: one actor per selected panel/tab; leaving the panel or logging out closes its scope and interrupts state-owned client work; reload discards local state. An interrupted HTTP request does **not** roll back a server commit. When a command returns a typed conflict, the authored machine re-reads the authorized server record and asks for a new decision; it must not replay the stale event automatically. The server validates payloads, authenticates and authorizes each operation, enforces versions, and owns transactions. Reactive `can` is only a preview. Inspection and telemetry publish bounded operation names/outcomes, never raw actor state, form contents, or bearer values.

**Second vertical slice:** an authenticated order-preparation panel in [Orders/Invoices](../examples/orders-invoices/README.md). Unlike the public one-write intake, it needs `billing.getOrder`, repeated `billing.addLine`, and `billing.issueInvoice`, with an editor credential, current `expectedVersion`, and explicit `VersionConflict` recovery. Current inspection exposes the operation's version input, typed conflict/error schemas, and subject policy (`bun run examples/orders-invoices/main.ts inspect billing.addLine`); it does **not** supply a UI-phase graph. Test a second editor's intervening write, forbidden reader, hidden foreign-tenant order, logout during lookup, duplicate submission, reload, and an ambiguous response after an authoritative commit. Compare an authored machine to a plain scoped Effect/local-state implementation before extracting a host: if the machine adds no clear lifetime or sequencing value, retain the simpler path. [Report Exports](../examples/report-exports/README.md) is a counterexample: its approval and execution states must stay in native durable workflow/outbox storage; a browser machine could only **display/poll** them.

Only after the two different interaction slices expose repeated, nontrivial host code should an API be promoted from example to UI adapter. A future declarative phase/form language would require separate evidence that its mappings are mechanical and lossless; this proposal does not authorize one.

**Evidence limit:** The completed intake probe's [dated live verification](wiki/validation-strategy.md#2026-09-25-transient-case-intake) and the exercised `support.advanceCase` inspection support the existing boundaries only. The proposed host, typed browser client, and Orders/Invoices panel have **not** been implemented or verified.
